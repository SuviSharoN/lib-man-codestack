Workflow Debugging Library Challenge

The Library That Broke on Opening Day

It is the first day of the new semester. The library team has just replaced its paper register with a digital system powered by a simple JSON file.

The desk is ready. The books are shelved. The students are waiting. Then the system starts behaving strangely.
Easy Level

1. Add Book Form Is Too Weak

A librarian tries to add a book with empty title, empty author, or a bad ID value.

The form still accepts the input and creates a broken record.

What to notice: The form should not allow obviously incomplete or invalid values.
Easy Level

2. Duplicate Book IDs Are Allowed

The same book ID is entered twice. The app allows it and creates confusion in the library list.

What to notice: The app should reject duplicates instead of silently accepting them.
Easy Level

3. Member Registration Accepts Broken Data

A student tries to register without email or department information.

The app still saves the member as if the data were complete.

What to notice: Missing important user information should be blocked early.
Easy Level

4. Search Returns the Wrong Book

A professor asks for book 105, but the system shows a different book entirely.

What to notice: The result should match the requested book, not a nearby one.
Easy Level

5. Clearing the Search Does Not Clear the Result

The user clears the input field, but the old result remains on the page.

What to notice: The UI should reset correctly when the input is empty.
Easy Level

6. Return Action Leaves the Book in the Wrong State

A user returns a book, but the book still appears borrowed.

What to notice: The state should be restored after a return action.
Medium Level

7. The App Sends a Different ID Than the User Typed

The user enters one ID, but the request goes out with a different value.

This is a flow bug: the value is being altered before it reaches the backend.

Medium Level

8. Borrow Changes the Wrong Record

A student borrows one book, but another book changes status.

The problem is not visible from the form alone. The correct record must be traced through the request flow.

Medium Level

9. The Search Logic Uses the Wrong Matching Rule

The app intends to find an exact match, but the logic behaves like a broader comparison instead.

Medium Level

10. The UI and Data Disagree

The form and the JSON state do not match after an action. The screen says one thing, but the underlying data says another.

Medium Level

11. The Details Panel Shows Missing or Wrong Data

The item exists, but the details section shows blank values or mismatched information.

This usually means the response and the UI contract are not aligned.

Hard Level

12. Borrow State and Book Status Drift Apart

The borrow log says a loan happened, but the actual book still appears available.

This is a deeper state bug and requires checking what really changed after the action.

Hard Level

13. The App Shows Success Even When the Action Fails

The user receives a success message after a broken request.

The UI is trusting the wrong signal instead of checking whether the underlying action really worked.

Mission

Your Task

Work through the list in order. Start with the easiest visible issues, then follow the data flow through the request and the JSON file. The goal is to understand the workflow, not memorize exact code patterns.

If the app is wrong, the cause is usually in one layer of the flow: input, request, logic, state, or response.
